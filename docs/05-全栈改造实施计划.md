## 0. 读代码得到的几个事实（决定了下面的方案）

- `src/core/` 确实是纯的：QuestFlow 在存档深拷贝上跑、`changed` 才提交、流水挂在 `f.history` 上。**原样搬到服务端执行没有障碍**，唯一碰到环境的是 `core/time/day.ts` 的 `dayKey()` 用了运行时的本地时区（见 1.2、Q1）。
- 界面层几乎只通过 `useGame(selector)` 读存档、调 `store/actions/*` 的函数改存档；只有 6 处在前端 `new QuestFlow(game())` 做**只读推导**（主线锁、暴击率、补签可用性、道具可装性）。所以前端改造的主战场是 `store/`，`ui/` 只加登录页、改设置页和告知页。
- 前端今天自己跑的「时间驱动」逻辑有三处：每秒的超时 / 护盾检查（`actions/exec.ts` 的 `onSecond`）、换日（`actions/session.ts`）、开机时的 `rollDay`。这三处都要变成服务端判定。
- 等 LLM 的地方：匹配（30s）、首段 / 重试 / 换目标拆解、结算后续拆 / 收官（90s / 段，两路并行）、聊天（45s，含会改存档的工具 `swap_quest` / `adjust_plan`）、视觉校验（30s，后台）。`agent/copy.ts` 的台词入口目前没有调用点。
- 证据今天是「选图 → 压缩 → 立刻入槽（unverified）→ 后台校验 → `applyVerdict`」，交单时前端等在途校验 ≤20s。服务端版要保住这个节奏。

## 1. 第三节七条：建议与理由

### 1.1 框架 —— 同意「建议」：Vite SPA + Hono + Drizzle + better-sqlite3 + zod + npm workspaces

- **不迁 Next.js / RR7 framework mode**。理由：现有前端是场景状态机驱动（无 URL 路由，`popstate` 映射成关叠层）、斜切转场、Canvas 粒子、常驻音频总线，全部是「一个长寿命页面」的写法；一体化框架的价值（SSR、文件路由、Server Actions）这里一样都用不上，反而要处理 hydration、RSC 边界、`'use client'` 满天飞，以及 vite-plugin-pwa 的替代方案。迁移代价高、收益为零。
- 后端 **Hono**（`@hono/node-server`）：`app.request()` 能直接做接口测试（第七节要求），自带 SSE（`hono/streaming` 的 `streamSSE`）、Cookie、body limit 中间件，和 zod 配合轻。
- **Drizzle + better-sqlite3（WAL）**：同步 API 正好配合「每用户串行写」（一个事务内读存档 → 跑 QuestFlow → 写回，不会被 await 打断）；`:memory:` 跑测试。Node 22 自带的 `node:sqlite` 仍是实验特性，不用。
- 密码哈希用 **`@node-rs/argon2`**（预编译二进制，`node:22-slim` 里不需要编译工具链）。
- 服务端打包：**esbuild** 把 `apps/server` + `packages/core` 打成一个 `dist/server.mjs`（`better-sqlite3`、`@node-rs/argon2` 标 external）。开发时用 `tsx watch`。
- 目录：

```
packages/core/      原 src/core（零改动搬家 + dayKey 加时区参数），外加前后端都要用的纯逻辑：
  src/shared/         自伤闸门（guardrail 的 isCrisisText / CRISIS_* 台词）、拆解失败卡文案（planFailTitle / planFailLine）、
                      聊天消息类型与上限（ChatMessage / CHAT_MAX_CHARS）、StatusSummary、API 契约（zod schema + 类型）
apps/server/        Hono 应用
  src/agent/          原 src/agent 搬过来（llmClient 去掉 CORS 探测；其余不改逻辑）
  src/db/             Drizzle schema、迁移、连接（WAL、foreign_keys）
  src/auth/           密码、会话、邀请码、限流
  src/repo/           存档（主档 / bak / corrupt）、流水、聊天、记忆、证据、快照、设置、同意
  src/flow/           意图处理器（每个意图 = 锁内 读档 → 换日 → 超时 → QuestFlow → 写回）
  src/jobs/           拆解任务、视觉校验任务、用户事件总线（SSE）
  src/routes/         /api/*
  src/cli/            create-admin、invite、reset-password、backup
  tests/              接口测试（:memory: + app.request()）+ 原 tests/agent
apps/web/           原前端（src/ui、src/audio、src/design、src/store 改写、public、index.html、vite 配置）
scripts/check-dist.mjs  扩展（见 6.4）
```

### 1.2 规则在哪执行 —— 同意「服务端权威」，补充三点

1. **时间**：所有意图里的 `now` 一律取服务器 `Date.now()`；客户端不传时间。每个响应带 `serverNow`，前端算出时钟偏差 `skew`，界面走秒用 `Date.now() + skew - startAt`，断网时照样走（只读）。
2. **时间驱动的事由服务端「懒判定」**，不跑定时任务：任何一次带登录态的请求进来，在锁内先 `rollDay(now)` 再 `checkTimeout(now)`（最多连跑两次：护盾碎 → 顺延后仍过点 → 判负，与今天「杀进程重开」的行为一致）。前端本地走秒到截止时刻发一次 `POST /api/flow/tick`，跨过 0 点 / 回到前台发 `GET /api/state`，由服务端给结论。**暴击随机数**只在服务端 `settle` 里取（`crypto.getRandomValues` 包成 `Rnd`）；`forceCrit` 不对外暴露。
3. **换日的「日」按用户时区算**：`dayKey(ms, tz)`，`tz` 存在账号上（Q1）。QuestFlow 构造时传 `{ rnd, tz }`，core 里所有 `dayKey(now)` 改成 `dayKey(now, this.tz)`；用 `Intl.DateTimeFormat`，前后端都能跑，不碰 Node API。

**串行与版本号**：
- 每个用户一个进程内的 Promise 链锁（单进程部署，够用；SQLite 事务再兜一层）。意图处理全程同步（better-sqlite3），锁只在「读档 → 跑流程 → 写回」这一小段持有；**LLM 调用不持锁**，回来后重新拿锁、重读最新存档、校验前提（同一个目标 / 还是那一单）再落库——等价于今天的「迟到回包按 token 丢弃」。
- 存档行带 `version`（每次写 +1），每个响应和 SSE 都带上。冲突策略建议**「按意图语义校验」而不是「整档乐观锁」**：意图里带上它针对的对象（`serial` / 道具 id），服务端对照最新存档判断还成不成立（这单还在队里吗？还是这一单在执行吗？），不成立返回 `409 stale` + 最新状态，前端刷新并 toast「另一台设备刚改过，已同步」。理由：后台视觉校验、另一台设备的换日都会让 `version` 变，整档乐观锁会让「装道具」这种无冲突操作也被误拒；而语义校验能精确拦下真正的冲突（两台设备同时接同一单 / 同时交同一单）。另给所有写意图一个客户端生成的 `intentId`（10 分钟内去重），防网络重试导致买两次。
- 导入、重置这两个整档覆盖操作额外要求 `baseVersion` 严格相等。

### 1.3 数据怎么存 —— 同意「建议」

- 每用户一行存档：`data`（`stringifySave` 的串）+ `bak`（上一份好串）+ `schema_v` + `version`。读写全部复用 `parseSave / saveFromJson / stringifySave`，「在默认值上合并」不变。
- 坏档：读到 `data` 解析不了 → 原串另存 `save_corrupt` 表 + 记日志（不打内容）→ 用 `bak` 恢复并立刻写回 → 响应里 `source: 'backup'`，前端照今天的样子提示一句；`bak` 也坏 → `source: 'corrupt'`，**不静默清零**：返回 `500 save_corrupt`，前端停在开机屏给「数据读不出来，联系管理员」，管理员用 CLI 处理。
- 流水、聊天、长期记忆、证据元数据、LLM 设置、同意记录、用量计数各自建表；证据照片存磁盘 `data/uploads/<userId>/<随机id>.jpg`；导入前快照存磁盘 `data/snapshots/<userId>/pre-import.json`（含 Base64 照片，可能好几 MB，不进库）。
- 迁移：Drizzle Kit 生成 SQL 迁移文件入库，服务启动时 `migrate()`；存档 JSON 内容靠 `v` 字段自管（目前仍是 v1，不动）。

### 1.4 账号 —— 同意「建议」，细化

- 用户名（3–20 位，字母数字下划线和中文，大小写不敏感唯一）+ 密码（≥8 位）；`@node-rs/argon2` 的 argon2id 默认参数。
- 会话：随机 32 字节 token，Cookie 只放 token，库里存 `sha256(token)`；`httpOnly; Secure; SameSite=Lax; Path=/`；30 天、滑动续期（每天最多续一次写库）；退出登录 / 改密码 / 管理员重置密码时吊销该用户全部会话。
- 邀请码：CLI 生成，**一次性、7 天过期**，库里存哈希；注册时校验并核销（同一事务）。
- CLI（`npm run admin -- <命令>`）：`create-admin`、`invite [--days 7] [--note 名字]`、`invites`（列出未用的）、`reset-password <用户名>`、`disable <用户名>`、`backup`。
- 管理员角色**没有任何应用内界面**，也不能在 App 里看别人的数据；它只是 CLI 里的一个标记。
- 不做：找回密码邮件、第三方登录、手机号。App 内提供「修改密码」（旧密码 + 新密码），见 Q6。

### 1.5 LLM 和 Key —— 同意「建议」，细化

- 服务端读环境变量 `LLM_BASE_URL / LLM_API_KEY / LLM_TEXT_MODEL / LLM_VISION_MODEL`（可空）。
- 用户覆盖**整套生效**：用户填了自己的端点 + Key，就用他自己的端点 / Key / 文本模型 / 视觉模型；没填就整套走服务器默认。**不允许「用服务器的 Key + 自选模型」**（防止朋友挑贵模型刷你的额度）。温度、视觉校验开关是个人设置，两种模式下都生效。
- 用户 Key 用 AES-256-GCM 加密存库（`APP_ENCRYPTION_KEY`，32 字节 Base64，环境变量）；接口只回 `hasOwnKey` 和末 4 位（`sk-…abcd`）用于确认填的是哪把，永远不回明文；Key 输入框只写不读，留空保存 = 不改。
- 【测试连接】改成服务端代测：`POST /api/llm/test`，可带一份「未保存的表单」去测；文本 / 视觉各一行结果不变。
- 失败分类沿用：`noKey`（服务器没配默认、用户也没填）、`noConsent`、`network`、`timeout`、`httpError`、`badResponse` + 拆解层的 `noPlan / badShape / badPlan / badGoal`。`cors` 在服务端不会出现，类型保留但不再产生；CORS 探测代码删掉。**新增 `quota`（超额 / 限流）**，文案见 Q2。
- 限流（进程内令牌桶）+ 每日上限（`llm_usage` 表按「用户 × 用户时区的日历日」计数），数值见 Q2。
- 拆解改成任务：`POST /api/plan/jobs` → 返回 `jobId` → 进度走 SSE（`stage 0 匹配 / 1 拆这一段 n/2 路 / 2 规则校验`，与 `PlanProgress` 同形）→ `done`（带新状态）或 `failed`（带 `PlanFailure` 的 code + detail）。前端 `withPlanJob` 保留外形（整屏加载卡 + 防连点 + 迟到丢弃），内部改成「发任务 + 等 SSE」。服务端同一用户同时只跑一个拆解任务，第二台设备打开时能接上同一个任务的进度。
- 匹配（≤30s）做成同步接口，不走任务（它不改存档，只返回类目和访谈卡）。

### 1.6 离线 —— 同意「建议」

- 外壳照旧离线可开。前端把最近一次 `StateView`（存档 + 流水 + 档案要用的数据）缓存进 IndexedDB（按 userId 分键，退出登录清掉）。
- 断网：开机读缓存进大厅 / 档案 / 主线页只读；执行页计时照走；所有写操作（按钮）点下去 toast「需要联网」并保持原状，不排队；顶部出一条细的离线提示。恢复联网自动 `GET /api/state` 刷新。
- 断网时到点：前端不判负，只显示「00:00 · 联网后结算」；联网后由服务端按服务器时间判（与 1.2 一致）。

### 1.7 旧数据 —— 同意「建议」

- 登录后在设置里「导入存档」，上传现有 PWA 导出的 JSON；服务端复用 `checkBundle`（格式 / 版本 / 每张照片 Base64 与类型）→ 不合格 400 且不动数据 → 合格先把当前数据导出成快照写盘 → 单事务整体覆盖（存档 / 流水 / 聊天 / 记忆 / 证据表 + 磁盘照片）。
- 导入接口 body 上限 50 MB（照片 Base64 在里面）；照片逐张验 magic bytes（JPEG / PNG / WebP），单张 ≤2 MB。

## 2. 表结构草案（SQLite / Drizzle）

所有业务表都有 `user_id`（外键 → users，`ON DELETE CASCADE`），所有查询都经过 `repo` 层、签名里强制带 `userId`。

| 表 | 主要列 | 说明 |
|---|---|---|
| `users` | `id` TEXT PK（随机）, `username` UNIQUE COLLATE NOCASE, `pass_hash`, `role` ('admin'/'user'), `tz`, `disabled`, `created_at` | |
| `sessions` | `id` = sha256(token) PK, `user_id`, `created_at`, `expires_at`, `renewed_at`, `ua` | 可吊销 |
| `invites` | `code_hash` PK, `note`, `created_at`, `expires_at`, `used_by`, `used_at` | 一次性 |
| `saves` | `user_id` PK, `data` TEXT, `bak` TEXT, `schema_v`, `version` INT, `updated_at`, `last_seen_at` | 一人一行 |
| `save_corrupt` | `id`, `user_id`, `raw` TEXT, `at` | 坏档原串留底 |
| `history` | `id` AUTOINC, `user_id`, `at`, `data` JSON | 索引 (user_id, at) |
| `chat` | `id` AUTOINC, `user_id`, `at`, `data` JSON | 每人保留最近 200 条 |
| `memory` | `id`, `user_id`, `text`, `at`, `source`, `weight` | 每人 ≤200 条（MEMORY_MAX） |
| `evidence` | `id` PK（服务端生成）, `user_id`, `file` 相对路径, `mime`, `bytes`, `sha256`, `taken_at`, `quest_serial`, `status`, `note` | 文件在 `data/uploads/<userId>/` |

| `llm_usage` | (`user_id`, `day`) PK, `text_calls`, `vision_calls` | 每日上限计数 |

不建表、放内存的：拆解任务状态（服务重启 = 在跑的任务丢失，前端按「网络断了」失败卡处理，可重试）、限流桶、意图去重缓存、SSE 连接。
偏好（静音 / 音量 / 看过安装引导）**留在设备本地**，不上服务器（它们本来就是「这台设备」的设置）。

## 3. 接口清单

约定：全部 JSON；写接口校验 `Origin`（必须等于 `APP_ORIGIN`）；入参一律 zod 校验；错误统一 `{ ok:false, code, message }`（`message` 是能直接念给宿主听的中文）。
**`StateView`** = `{ version, serverNow, tz, source, save: saveToJson(...) }`；所有改存档的接口都返回 `{ ok:true, state: StateView, events: FlowEvent[], ...专属结果 }`。
**`FlowEvent`**：懒判定顺带发生的事——`{kind:'rollDay'}`、`{kind:'shield', extendMin}`、`{kind:'timeout', outcome: FailOutcome}`——前端据此播护盾碎 / 弹超时失败页，和今天 `onSecond` 里的分支一一对应。

### 3.1 账号与会话

| 意图 | 路径 | 入参 | 返回 |
|---|---|---|---|
| 注册 | `POST /api/auth/register` | `username, password, invite, tz` | `me`（并种 Cookie） |
| 登录 | `POST /api/auth/login` | `username, password` | `me` |
| 退出 | `POST /api/auth/logout` | — | — |
| 改密码 | `POST /api/auth/password` | `old, next` | —（吊销其他会话） |
| 我是谁 | `GET /api/me` | — | `{ username, tz, consent: {version, at} \| null, consentVersion }` |
| 健康检查 | `GET /api/health` | — | `{ ok, db: 'ok' }`（不需登录） |

### 3.2 状态与意图（服务端跑 QuestFlow）

| 意图 | 路径 | 入参 | 专属返回 |
|---|---|---|---|
| 读状态（开机 / 回前台 / 跨 0 点） | `GET /api/state?boot=1` | — | `prevSeen`（boot 时：上次离开时刻，用来出「你走了多久」） |
| 到点检查 | `POST /api/flow/tick` | — | （events 里给 shield / timeout） |
| 接单（简报【开始计时】） | `POST /api/flow/accept` | `serial` | — |
| 装道具 | `POST /api/flow/equip` | `item` | — |
| 交单 | `POST /api/flow/submit` | `serial` | `result: QuestResult`, `followUp: {jobId} \| null` |
| 认输 | `POST /api/flow/give-up` | `serial` | `outcome: FailOutcome` |
| 领补救单 | `POST /api/flow/take-remedy` | `now: boolean` | `quest` |
| 再要一批日常 | `POST /api/flow/refill` | — | `added` |
| 购买 | `POST /api/flow/buy` | `item` | — |
| 补签 | `POST /api/flow/patch` | — | — |
| 佩戴称号 | `POST /api/flow/wear` | `title` | — |
| 拆解失败「先跳过」 | `POST /api/flow/skip-plan` | `text` | — |

所有写意图另带 `intentId`（去重）。前端的拦截提示（主线锁、晶核不够、补签不可用原因…）照旧在前端用共享 core 先算一遍给即时反馈，服务端再按同一套函数校验一遍（不成立回 `409 / 422`，`message` 用同一句原因）。

「交单」的服务端时序（保住 G4.1 与证据规则）：拿锁 → 校验 `serial` 是当前执行中的单 → **释放锁**等这单在途的视觉校验（≤20 秒，到点没回来的按未校验）→ 重新拿锁 → 封存 → `settle` → 写档 + 流水 → 如果 `windowEnd / finale`，起一个续拆 / 收官任务、把 `jobId` 带回 → 前端先显示加载卡等任务结束，再演结算（与今天「先拆后演」一致）。

### 3.3 证据

| 意图 | 路径 | 入参 | 返回 |
|---|---|---|---|
| 上传一张 | `POST /api/evidence` | multipart：`file`（前端已压成 JPEG）, `serial` | `state` + `shotId`（已入槽 unverified，后台开始校验） |
| 撤一张 | `DELETE /api/evidence/:id` | — | `state` |
| 看图 | `GET /api/evidence/:id` | — | 图片本体（`Cache-Control: private`），非本人 404 |
| 开发用演示截图 | `POST /api/dev/demo-evidence` | — | 只在 `NODE_ENV !== 'production'` 时注册路由 |

上传校验：≤2 MB、magic bytes 是 JPEG、文件名服务端生成、路径只由 `userId + 随机 id` 拼、执行中有这一单且没封存、≤3 张。视觉校验结论通过 SSE 推 `verdict {id, result: kept|rejected|gone, status, note}`，前端照今天的方式出 toast / 「上一张被拒：…」/ 她的台词。

### 3.4 拆解与 LLM

| 意图 | 路径 | 入参 | 返回 |
|---|---|---|---|
| 匹配类目（绑定第一步） | `POST /api/plan/match` | `text` | `{ catId, cards }` |

自伤闸门：`/api/plan/match`、`/api/plan/jobs`、`/api/chat` 入口先过 `isCrisisText`，命中直接返回关怀台词、不调 LLM、不计用量。

### 3.5 聊天、流水、数据

| 意图 | 路径 | 入参 | 返回 |
|---|---|---|---|
| 聊天记录 | `GET /api/chat` | — | `messages`（≤200） |
| 发一句 | `POST /api/chat` | `text`（≤200 字）, `scene` | `messages`（新增的）+ `state?`（工具改了存档时） |

| 流水 | `GET /api/history` | — | `entries` |

### 3.6 实时通道

`GET /api/stream`（SSE，每个已登录页面一条）：`state {version}`（别处改了存档 → 前端拉新状态）、`job {id, progress}` / `job.done {id, state}` / `job.failed {id, failure}`、`verdict {...}`、每 25 秒心跳。页面切后台断开，回前台重连并 `GET /api/state` 补齐。

## 6. 安全与工程细节

1. **用户隔离**：`repo` 层每个函数第一个参数是 `userId`，SQL 一律 `WHERE user_id = ?`；按 id 取资源时「不存在」和「不是你的」都回 404。每个资源类接口都有一条 A/B 交叉测试。
2. **日志**：自写的小日志器，统一脱敏（`authorization`、`cookie`、`apiKey`、`key_enc`、图片 Base64 / 二进制一律不打）；请求日志只记 方法 / 路径 / 状态 / 耗时 / userId。
3. **反代**：`TRUST_PROXY=1` 时才信 `X-Forwarded-For`（限流按 IP 用）；`APP_ORIGIN` 必填（Origin 校验和 Cookie 的 Secure 都靠它）。
4. **`check:dist` 扩展**：web 产物里不许出现 LLM 端点路径、`Authorization` 头拼接、`sk-` 样式串；构建时若环境里有 `LLM_API_KEY` / `APP_ENCRYPTION_KEY` / `SESSION_SECRET`，逐字扫描它们的值不在产物里；server 产物里不许有硬编码的默认端点 / Key。
5. **`.gitignore`** 增加 `data/`、`backups/`、`apps/*/dist/`。
6. **文件行数**：每个文件 ≤600 行照旧；`questFlow.ts`（577 行）加 tz 只改几行，不会超。

## 7. 需要你拍板的规则问题（两边都没写到）

**Q1 · 「一天」按哪个时区算？**（影响换日、连胜、补签、日常发放、每日额度）
建议：按**每个账号自己的时区**。注册时自动取浏览器时区存进账号；之后只能管理员 CLI 改（防止有人改时区刷连胜 / 补签）。导入旧存档里的日期照原样用（你和朋友应该都在同一时区，旧档不会错位）。
备选：全站统一一个时区（`APP_TZ`，默认 Asia/Shanghai）。更简单，但朋友若在别的时区，0 点换日会错位。

**Q2 · LLM 额度给多少？超了怎么办？**
建议（只对**用服务器默认 Key** 的人生效；用自己 Key 的人只限速、不限每日总量）：
- 限速：每人每分钟 10 次文本请求、10 次视觉请求（一次拆解两路并行算 2 次）。
- 每日上限：文本 150 次、视觉 60 次（大约能拆 3–4 次目标 + 聊 100 句 + 验 60 张图）；你自己的账号（admin）不设上限。数值做成环境变量。
- 超了的表现：
  - 拆解 / 匹配：失败卡新类型 `quota`，标题「今天额度用完了」，她的台词「今天的份额用完了。[明天再来]，或者去设置里填你自己的 Key。」——答案照旧保留、可「先跳过」。
  - 聊天：不调模型，回一句「今天聊太多了，额度用完。[明天再说]。」（走今天的兜底台词通道，不算报错）。
  - 视觉校验：**按「未校验」照收**（评级最多 B，和关了视觉校验同口径），她说一句「今天验图的额度用完了，先按[未校验]收」。
  你要确认：数值、以及「视觉超额按未校验收、评级受影响」这一条能不能接受。

**Q3 · 拆解在服务端跑完就落库——关掉页面也算数？**
今天拆解跟着页面走，页面关了就没了。服务端版任务会继续跑：比如绑定仪式拆到一半关掉 App，任务成功会照常落库（主线进在手、见面礼、访谈记忆），下次打开直接进大厅；失败则下次打开回到绑定仪式（答案不保留，和今天一样）。
建议：接受这个变化（更不容易丢东西）。

**Q4 · 两台设备同时开着**
建议：两边都实时同步（SSE 推版本号 → 自动拉新状态）。一台设备上的执行页、结算演出、失败页只在**发起操作的那台**演；另一台只是静默刷新到新状态（比如回到大厅、执行中药丸消失），并 toast 一句「另一台设备刚交了一单」。两台同时交同一单 → 后到的那台收到「这一单已经交过了」。你确认这个体验就行。

**Q5 · 告知页的新文案**（`CONSENT_VERSION` → 2，所有人首次登录都要签）
建议五条：
| 项 | 新说法 |
|---|---|
| 存档 | 等级、主线、记录、照片存在**这台服务器**上，换设备登录还在 |
| 目标原文与访谈答案 | 经服务器发给服务器配置的模型服务商（或你自己填的服务商），拆成任务清单 |
| 聊天内容 | 同上，生成她的回复 |
| 证据照片 | 压缩后存在服务器，并发给视觉模型核对；只有你自己的账号能看到 |
| 谁能看到 | **服务器管理员在技术上能接触到数据库和照片**；App 里不提供任何查看别人数据的功能 |
最后一条是我加的，因为照实说更符合「道具文案说真话」的定案精神；你决定要不要写、怎么措辞。

**Q6 · 账号相关的几个小口径**
- 宿主名：HUD / 开机日志里的名字继续用存档里的「宿主」，不用登录用户名。（建议）
- App 内可以「修改密码」（旧密码 + 新密码，改完其他设备下线）。忘了密码才找管理员。（建议）
- 退出登录：清掉这台设备上的离线缓存；偏好（音量等）保留。（建议）
- 删除账号：只走 CLI（`disable`），App 内不提供。（建议）

**Q7 · 导入别人的存档**
导出包里没有账号信息，所以朋友 A 的导出文件可以被导入到 B 的账号（相当于转移进度）。建议：允许，不做绑定。
