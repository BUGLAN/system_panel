## 0 · 一页速览

```
今天：  目标 = 一句话 + [8 个环] + 天数        环 = 工作单元（1 环 = 1 张单）
之后：  目标 = 一句话 + 期限 + 进度            任务 = 唯一的工作单元
        周期计划 = 系统按周期发布任务          ← docs/16 有、代码里从没有的那一层
        主线页 = 目标抬头 + 任务卡片（新设计）
        环场   = 8 条等宽虚线 → 1 条进度带
```

**结论：宿主是对的。**「环」这一个概念同时兼三个互相绑死的身份，所以任何目标都得同时满足
「切成 5~8 格」和「每格一次做完」——而"半年内坚持健身"两条都不满足。

## 1 · 为什么废（不是审美，是模具不对）

### 1.1 三个身份绑在一起

| 身份 | 代码 | 它强制了什么 |
|---|---|---|
| 数据结构 | `Goal.rings`（`List<GoalRing>`） | 目标必须切成 **5~8 格**（`kNextGoalMinRings/MaxRings`）|
| 工作单元 | `QuestFlow.ringTask(i)` | 每格必须是**单次可执行**（title / proof / minutes）|
| 视觉 | `RingField` + `RingLabels` + `RingTag` | 她身上 8 条椭圆 + 8 条挂签 + 1 枚当前环标签 |

### 1.2 真实数据暴露的后果

2026-10-12 用真端点拆「半年内坚持健身」，模型给出的是**正确的**周期性计划：

```
「一周内完成 3 次 30 分钟训练」   被记成 → 一个环 · 45 分钟
「连续 4 周每周三练后测 5 公里」 被记成 → 一个环 · 60 分钟
```

不是模型拆错了，是**模具只接受"单次动作"**。跨度两周到一个月的承诺，塞进一个
`minutes` 字段里，等它变成派单，宿主收到的是"60 分钟"，实际要干四周。

### 1.3 顺序也是被硬编码死的

```dart
// quest_flow.dart:404  队列里只钉「当前那一环」的一张主线单
if (ci >= 0) queue.add(ringTask(ci));

// quest_flow.dart:764  做完这张 → 这一环 done → 下一环 cur → 补单入队
queue.insert(0, ringTask(nx));
```

队列里**同一时刻只有一个主线单**（`removeWhere(kind=='main')` 再插当前环），
所以"只能一环一环来做"。而宿主要的是「任务却能做不同的」。

> 附注：`accept()` 其实**完全不判环**（不拦），"唯一执行中"是靠 `_active` 只有一个槽 ——
> 也就是说**"必须按顺序"这件事根本没有代码在守，只是队列只发一张主线单**。
> 这条很重要：解绑顺序的改动比想象中小。

## 2 · 废除后是什么（新模型）

| 概念 | 今天 | 之后 |
|---|---|---|
| **目标** | 一句话 + 8 个环 + 天数 | 一句话 + **期限** + 进度（`Goal` 瘦身）|
| **周期计划** | ❌ 从未实现 | ✅ 系统按周期发布任务（`任务数 = 天数-1`，docs/16）|
| **任务** | 主线 / 日常 / 补救（`kind: main/daily/remedy`） | **唯一工作单元**，来源标注属于哪个目标 |
| **进度** | 第 N/8 环 | 完成数 · 连击 · 六维 · 期限内推进度 |
| **环** | 三合一 | **概念消失**：视觉→进度带，进度→完成数，工作单元→任务 |

### 2.1 宿主那句话的两种读法（要你挑）

| | 方案 A：环 → 改名任务 | 方案 B：环概念消失，任务接管（**推荐**）|
|---|---|---|
| 做法 | `GoalRing` → `Task`，去掉顺序锁 | 环整层删掉，任务由周期计划产出，数量不固定 |
| 改动 | 小（改名 + 解绑顺序）| 大（数据模型 + 生成 + 结算 + UI）|
| 目标拆解 | 仍是固定的 5~8 格 | 可以是"未来 7 天的任务清单"，条数由期限算 |
| "半年坚持健身" | 仍然别扭（还是 8 格）| 自然（第 1 个月 N 张单）|
| 评价 | 保留模具，只换了标签 | **换掉模具** |

**我推荐 B，理由**：A 只解决了"名字"，没解决"固定 5~8 格 + 每格单次"这两条，
而这两条正是 1.2 那个荒诞结果的成因。B 的第 1 阶段天然包含 A 的改名工作，所以
选 B 不会白干；选 A 则大概率要再做一次。

### 3.3 状态（⑨ 状态线 + 可交互）

| 状态 | 视觉 | 可交互 |
|---|---|---|
| **待发布** | 状态线暗青 + 牌面半透明 | ✗（"系统还没派"）|
| **可接** | 状态线亮青、领位抬起 −16px + 外辉 α60/blur22 | ✓ 按住接单 |
| **执行中** | 状态线亮青**呼吸**（2.6Hz）+ 顶部计时 | ✓（进执行面板）|
| **已提交待验** | 状态线金 + 角标 `待验` | ✗ |
| **已完成** | 状态线实心 + 压印朱砂 | ✓（只读回顾）|
| **已放弃** | 灰 + opacity .35 + 原因角标 | 点 = 她解释一句，不落定 |

### 3.4 用哪个牌阵（复用已落地的两个，零返工）

| 位置 | 阵 | 尺寸 | 为什么 |
|---|---|---|---|
| 主线页主体 | **轨 · 铭牌轨** | W 268×58 | 已落地、支持滑动换领位、一屏 5~6 条 —— 任务数量不定时最合适 |
| 点领位 → 详情 | **L 大牌**（审视态 ×1.25）| 208×292 | 复用 docs/32 §4.3 的审视态，翻背面看"来龙去脉" |

**为什么不用扇阵**：扇阵是"命运级选择"（2~4 张）；主线一天可能有十几张单，
扇阵铺不下，而且"从 N 个挑 1 个"的语义也不对 —— 这里是"看清单 + 挑一个做"。
