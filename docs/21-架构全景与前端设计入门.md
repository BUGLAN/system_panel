## 0 · 三句话

1. **这个仓库是「双真源」结构**：`prototype/opus-v2-dir/`（HTML/CSS/JS 原型）是**规格真源**——视觉、动效、手感都先在原型上定死；`app/`（Flutter）是**交付真源**——把原型逐像素、逐毫秒搬成 iOS/Android 双端 App。原型改 → App 跟着改，反过来不行。
2. **技术栈就一句话**：Flutter/Dart 单代码库双端 + 全自研组件（零 UI 框架、零状态管理库）+ Live2D 人物 + OpenAI 兼容 LLM（DeepSeek）+ SharedPreferences 本地存档；后端只有原型期的一个 Node 静态服务兼 LLM 代理。
3. **你不懂前端设计这件事，恰好是这个项目的核心风险**——因为这是个「视觉与手感驱动」的产品（辉光、玻璃、弹簧、逐帧结算演出），而不是一个 CRUD 后台。所以本文第三部分的学习清单，是**能直接落到这个仓库文件上练**的那种。

### 1.3 运行时：App 是怎么叠出来的

`main.dart` 的核心是一个 `Moment` 状态机：

```dart
enum Moment { boot, lobby, onboard, dispatch, exec, result, fail, sheet, main }
```

九个时刻（开机 / 大厅 / 绑定仪式 / 派单 / 执行 / 结算 / 失败 / 面板 / 主线）叠加在同一棵 Widget 树上，视觉层次自下而上：

| 层 | 文件 | 职责 |
|---|---|---|
| ① 天幕 | `widgets/bg_layer.dart` | 底图 + 网格 + 扫描线 + 噪点（多层叠加，常驻渲染） |
| ② 她本人 | `stage/live2d_web.dart` → `assets/stage/stage.js` | Live2D 舞台（WebView 平台视图），外加 `ring_painter.dart` 画的环套在她身上 |
| ③ 界面 | `widgets/*.dart` | 委托板、执行面板、结算面板、失败页、面板页、主线时间轴、底栏、HUD |
| ④ 特效 | `widgets/fx_layer.dart` / `fx_particles.dart` | 亮帧、震屏（`ShakeLayer`）、粒子（`CustomPainter` + `Ticker`） |
| ⑤ 遮罩 | `main.dart` | 暗场（veil）、过渡 |

**一条铁律**（架构级约束，不是审美偏好）：**平台视图（Live2D 的 WebView）不能被 `Transform`/`Opacity` 包裹**——`saveLayer` 会把它吞掉。所以 `fx_layer.dart` 的震屏必须写成「不抖的时候不套 Transform」。这条纪律在 `app/STAGE-OPTIONS.md` 与 HANDOFF 里各写了一遍。

### 1.4 数据流：一次「接单 → 提交 → 结算」走哪些文件

```
① 派单    goal_gen.dart  rollDayQueue / pickDailies      → 从模板池挑单、按日上限 6 排班
② 展示    widgets/plate.dart                             → 全息委托板（落板过冲 + 稀有度骰子）
③ 接单    widgets/hold_button.dart（按住 0.9s）→ quest_flow.dart accept()
④ 执行    state/app_clock.dart 走秒 → widgets/exec_panel.dart（计时 + 证据槽 ≤3 张）
⑤ 校验    agent/vision.dart  拍照 → 压缩 JPEG80 → 多模态判「像不像」→ 已校验/存疑/未校验
⑥ 结算    quest_flow.dart settle() → data/rewards.dart（EXP/金币/暴击）→ widgets/result_panel.dart 演出
⑦ 落档    state/save_file.dart（save/v1）+ agent/memory.dart（memory/v1）+ history/v1
⑧ 触达她  agent/copy.dart（文案四入口，逐字回退）· agent/llm_client.dart（聊天/工具调用）
```

设计原则上有一句总结：**「数值只能经结算产生」**——LLM 工具（`agent/tools.dart`）不允许直接改经验/金币，只能走结算链路。这是把 AI 当成「嘴」而不是「手」的架构选择。

### 1.5 为什么原型要留着（而不是「搬完就删」）

1. **原型是唯一可快速试错的地方**：改 `app.css` 里一个弹簧曲线，浏览器刷新即见；在 Flutter 里同样的改动要热重载 + 真机截图对比。
2. **原型是「无可辩驳的证据」**：`docs/20 §7.3` 那场「结算演出 3.85s 超规格」的争议，裁决依据就是「原型即规格」这条宪法条款。
3. **原型是动效的可执行文档**：`motion-demo/index.html` 里的定时与曲线，就是 Flutter 侧的验收标准。

### 1.6 「网页前端」和「Flutter 前端」差在哪（给工程师的类比）

| 概念 | 网页（原型） | Flutter（App） | 本项目里的对应 |
|---|---|---|---|
| 元素 | DOM 节点 | Widget（不可变描述） | `widgets/*.dart` |
| 布局 | CSS Flexbox / Grid | Widget 嵌套（`Row`/`Column`/`Stack`）+ 约束向下传递、尺寸向上回传 | `main.dart` 的 `Stack` 分层 |
| 样式 | CSS 类 + 变量 | Dart 常量 + `ThemeData` | `design/tokens.dart` ↔ `app.css :root` |
| 重绘 | 浏览器合成层 | Widget 重建 + `RenderObject` 重绘 + GPU 光栅 | `CustomPainter`（`ring_painter` / `radar` / `fx_particles`） |
| 动画 | CSS `@keyframes` / `transition` | `AnimationController` + `Tween`/`SpringSimulation` | `stage/spring.dart` ↔ CSS `linear()` 弹簧 |
| 状态 | JS 变量 + DOM 事件 | `setState` / `ChangeNotifier` / 状态管理库 | 各 `state/*.dart` store |

**关键差异（也是最容易踩的坑）**：网页里「改一下 CSS 就是改渲染」；Flutter 里「改一下 Widget 就是重建整棵子树」，重建时的 `key` 若变化会导致状态丢失——本项目历史上最严重的 bug（「提交任务卡死」）就出在这里：`fx_layer.dart` 的震屏在切换 `Transform` 分支时把整棵子树重挂，印章一砸就从头重播，形成死循环（修法：`GlobalKey(KeyedSubtree)` 钉住子树）。

## 2 · 术语扫盲：前端设计到底在说什么

> 这一节是给「完全不懂设计」的人写的。目标不是让你变成设计师，而是让你**看得懂设计稿、说得出术语、能判断好坏**。

### 2.1 设计 = 三分手艺 + 一分审美

外行以为设计是「配色调好看」。业内把它拆成四件事，前两件是**确定性的手艺**（可学、可用规则检验），后两件才涉及审美：

| 手艺 | 解决的问题 | 本项目里的例子 |
|---|---|---|
| **排版 Typography** | 文字层级：谁大谁小、谁粗谁细、行距多少、一屏几级 | 标题 ShuHei / 数字 Tektur / 正文 FangYuan / 读数 Kode Mono —— **四种字体各管一件事**，这就是排版决策 |
| **间距与布局 Spacing & Layout** | 元素之间的关系：贴得近=相关，离得远=无关；对齐=秩序 | 顶距从 96→64→20px 的三次收紧（AGENTS.md v12/v14），每次都是「把空间还给内容」 |
| **颜色 Color** | 情绪 + 层级 + 状态；深色下还有对比度硬指标 | 唯一主色电光青 `#38E1FF` 只做强调；稀有度七色**只出现在稀有度本身上**，不做氛围 |
| **动效 Motion** | 因果与连续性：谁从哪来、去哪、什么在响应我 | 弹簧 k=120/ζ=0.9、亮帧 180ms、打字机 34ms/字 |

### 2.2 你会反复听到的 12 个词（速查）

| 术语 | 大白话 | 备注 |
|---|---|---|
| **Design Token（设计令牌）** | 把颜色/字号/间距/圆角/时长写成变量，全站引用 | 本项目的 `app.css :root` ↔ `tokens.dart`；**token 是设计与代码的合同** |
| **Type Scale（字阶）** | 一套固定档位的字号（如 12/14/16/20/28/46） | 禁止「随手写 17px」；禁止正文字体做数字 |
| **Spacing Scale（间距阶）** | 一套固定的间距档位（4/8/12/16/24/32…） | 让界面看起来「有节奏」的最省钱手段 |
| **Hierarchy（层级/视觉层次）** | 一眼看出谁最重要 | 靠大小、粗细、颜色、留白、位置实现，**不靠加框** |
| **Contrast（对比度）** | 前景与背景的亮度差；有 WCAG 硬指标（正文 4.5:1） | 深色 UI 的第一大坑，见 §3.2 |
| **Elevation / Depth（高度/纵深）** | 「这块浮在上面」的表达 | 深色下不能用阴影表达，要用**更亮的表面**（Material 的做法） |
| **Material（材质）** | 半透明/模糊/纹理的质感 | 原型里的玻璃面板；微软 Fluent 叫 Acrylic/Mica |
| **Glow / Bloom（辉光/泛光）** | 发光边缘 | 本项目主要视觉语言；滥用会让文字读不清 |
| **Easing / Curve（缓动曲线）** | 动画的速度变化 | 本项目禁用线性匀速；`cubic-bezier(.16,1,.3,1)` 是主力 |
| **Spring（弹簧）** | 带过冲的物理缓动，最接近真实 | `--spring` / `--soft` 两条 `linear()` 曲线 + Flutter 侧自研弹簧 |
| **Reduced Motion（降低动效）** | 尊重系统设置「减少动态效果」 | 系统级无障碍开关；原型有、App 侧尚缺（docs/20 TODO-23） |
| **Design System（设计系统）** | Token + 组件 + 规范 + 代码的整套 | 微软 Fluent、Google Material、Apple HIG 都是；本项目自研了一套小的 |

### 2.3 「Fluent」到底指什么——三种可能，别混

你说「fluent/dark」，这个词有三个完全不同的所指，先分清再决定学哪个：

| 可能 | 是什么 | 谁在用 | 你要不要学 |
|---|---|---|---|
| **① Fluent Design System（微软）** | 微软 2017 年提出的设计语言（Light/Depth/Motion/Material/Scale 五要素），后来演进为 **Fluent 2**（token 化的设计系统），也是 Windows 11 / Office / Teams 的实际规范 | 微软系产品、Windows 应用、部分 Web（Fluent UI React） | **值得当「设计系统怎么组织」的教材读**；但它解决的是「生产力工具的秩序感」，与你项目的「游戏 HUD 炫技感」气质相反。可借鉴的是它的**方法论**（token 分层、材质层级、动效三原则），不是它的外观 |
| **② fluid / fluent motion（流畅动效）** | 指「跟手、可打断、有惯性」的交互手感，代表文献是 Apple 2018 WWDC《Designing Fluid Interfaces》（[英文原版](https://developer.apple.com/videos/play/wwdc2018/803/) · [中文字幕版](https://developer.apple.com/cn/videos/play/wwdc2018/803/)） | iOS/macOS、所有做高质感交互的团队 | **强烈建议学**——这是你做这个 App 最需要的一课，比配色重要十倍 |
| **③ 英文词义「流利/流畅」** | 泛指不卡顿、顺滑 | 随口一说 | 忽略 |

**给你的判断**：这个项目应该学的是 **②（动效手感）+ Material/Apple 的深色规则 + 排版与间距基础**；**① Fluent 当方法论读一遍就够**，不必引入 Fluent 的组件库（它是给 Windows 生产力应用准备的，和你的深色辉光 HUD 不搭）。

### 2.4 「Dark」不只是把背景刷黑

深色 UI 有一整套与浅色不同的规则（为什么不能用纯黑 `#000`、层级怎么表达、品牌色为什么要降饱和、对比度硬指标是多少）。完整内容见 **§3.2**，先记住三条：

1. **别用纯黑 + 纯白**：纯黑 OLED 上会有拖影，纯白字在纯黑上会「晕开」（halation），长时间看更累。
2. **层级用「更亮的表面」而不是阴影**：深色底上阴影几乎看不见，Material 的做法是往表面叠一层白色半透明。
3. **对比度是硬指标，不是感觉**：正文 ≥4.5:1、大字 ≥3:1、非文本 UI 部件 ≥3:1（WCAG 2.2）。

### 3.1 微软 Fluent Design System

> 结论先给：**Fluent 值得花一个下午读，但不值得引进你的 App。** 它是「先想清楚层级/材质/动效/光源，再落成 token」的一套**方法论**，不是你要学的技术栈。

#### 3.1.1 它到底是什么

Fluent 是**三层结构**：设计语言（规则）→ 设计系统（token 化的规范）→ 组件库（React / Web Components / iOS / Android / Windows 各自实现）。官网原话：「Fluent's cohesive design language is carried through each platform-specific Fluent UI library」（[Fluent 2 · Develop](https://fluent2.microsoft.design/get-started/develop)）。

- **2017 年**微软把新一代视觉语言命名为 Fluent Design System（前身 Metro，代号 Neon），最初的**五大要素：Light / Depth / Motion / Material / Scale**（[官方归档博客](https://learn.microsoft.com/en-us/archive/blogs/shintak/fluent-design-2)）。注意这条关键定调：五大要素**不提供具体实现方法，是「思考方式的要素」**——所以它不是一份 CSS 清单。
- **Fluent 2（当前版）**把重心从「五大要素叙事」搬到 **token 体系**：[Global tokens](https://fluent2.microsoft.design/design-tokens)（原始值：hex、字级、圆角、动画）→ **Alias tokens**（语义名，如 `colorNeutralBackground1`），且每个 token 都给 light/dark 两套值（[Web Alias Color Tokens](https://fluent2.microsoft.design/color-tokens2) 是全站最有工程价值的一页）。
- 当前四条价值主张见 [Design principles](https://fluent2.microsoft.design/design-principles)，其中「**80% 复用平台原生组件，20% 精力做 signature experiences**」是 Fluent 2 最大的态度转变。

#### 3.1.2 它与 Windows / Web / Flutter 的关系

- **不专属 Windows**：官网 Components 区并列 Web / iOS / Android / Windows 四平台。Web 端官方实现是 `@fluentui/react-components`（React v9 + [Griffel](https://github.com/microsoft/griffel)）与 `@fluentui/web-components`（FAST Element），共享 token 包 `@fluentui/tokens`；Windows 侧是 [WinUI 3](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/)。
- **Flutter：官方没有实现。** pub.dev 上是第三方包 [fluent_ui](https://pub.dev/packages/fluent_ui)（作者 bdlukaa，4.16.1，3.23k likes，被标 Flutter Favorite），README 自述 **Unofficial** 且「我是唯一在维护它的人，PR 合并可能要等」。
  **判断：不要用它当 UI 基础。** ①它是**桌面 Windows 控件集**（NavigationView / CommandBar / 桌面 Acrylic），密度与交互假设是鼠标键盘；②单人维护，把整个控件层押在别人的业余时间上不合理；③你要的玻璃+辉光+斜切角，自己用 `BackdropFilter` + `CustomPainter` 更可控（Fluent 的 Acrylic 是**采桌面壁纸**的，移动端没有壁纸可采）。但它的 Acrylic 实现和主题分层**值得读源码**。

#### 3.1.3 这个项目真正该抄走的 5 件事

| # | Fluent 的概念 | 出处 | 在你的项目里怎么用 |
|---|---|---|---|
| 1 | **Acrylic 是「配方」不是「模糊」** | [Acrylic material](https://learn.microsoft.com/en-us/windows/apps/design/style/acrylic) | 配方 = 背景 → 模糊 → **exclusion 混合层（专门保文字对比度）** → 色调叠加 → **噪点**。你的玻璃面板现在若只有 `BackdropFilter(blur)`，请补「色调统一 + 极低透明度噪点」两笔——这比调 blur 有效得多 |
| 2 | **材质有使用纪律** | 同上 Do/Don't | 玻璃只用于**临时浮起的表面**（顶部面板、弹窗、结算卡、装备槽）；页面底色用实色；**不要并排贴多块亚克力**（有接缝）；**不要在亚克力上直接放强调色文字**（默认字号过不了对比度）。→ 一次解决「整屏都在发光反而没重点」 |
| 3 | **材质要有降级路径** | 同上 | Acrylic 是 GPU 密集、耗电大户，官方在节电模式/关透明效果/高对比模式下**全部退化为纯色**。→ 把毛玻璃与辉光做成**可整体降级的开关**（`MediaQuery.disableAnimations` + 自建省电模式），降级后 = 实色 + 描边，视觉语言不塌。**这是你目前原型最缺的一环** |
| 4 | **Elevation 是数字台阶** | [Elevation](https://fluent2.microsoft.design/elevation) / [Layering](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/layering) | Fluent 给固定 shadow ramp（2/4/8/16/28/64），Windows 侧是 Window 128 / Flyout 32 / Tooltip 16 / **Card 8** / Control 2 / Layer 1，且**光源方向必须一致**；Windows 还用 **1px 描边替代投影**勾勒边缘。→ 给你的「委托板 / 顶部面板 / 结算卡 / 弹窗 / 装备槽」各定一级，写进 `DESIGN.md`，把「浮多高」从感觉变成查表 |

**额外一条最贴合你「发光」语言的**：[显示焦点 Reveal Focus](https://learn.microsoft.com/zh-cn/windows/uwp/ui-input/reveal-focus)——官方拆解了「辉光如何沿元素边框流动」：**主边框 2px 在外、辅助边框 1px 在内、辉光粗细与主边框成正比；静止脉动、焦点移动时朝焦点方向流动**，还给了「只留辉光」的写法（主画刷透明 + 辅助厚度 0）。你 HUD 里按钮的悬浮辉光可以照这个结构做。

### 3.2 深色 UI（Dark）的设计规则与客观验证

> 来源全部为一手规范（Material / Apple HIG / W3C WCAG），**并且针对本项目的颜色实算了对比度**。这是本文最该先读的一节——因为你的 App 100% 是深色 UI。

#### 3.2.1 五条核心规则（带出处）

1. **不用纯黑当底**。Material 原话是「Use dark grey – rather than black」，推荐表面 `#121212`；纯黑只在省电场景用，且同一页给出官方警告：OLED 上像素开关会造成滚动时的**拖影**（[Material 2 · Dark theme](https://m2.material.io/design/color/dark-theme.html)）。你的 `#03060E` 属「带蓝的深灰」，方向是对的。
2. **不用纯白当正文**。Apple：「Soften the color of white backgrounds… to prevent the background from glowing in the surrounding Dark Mode context」——这就是**光晕（halation）**（[Apple HIG · Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)）。Material 给的正文对比度目标是 **15.8:1**，而不是纯黑白的理论上限 21:1。
3. **层级靠「表面变亮 + 描边」，不靠阴影**。Material 的经典解法是往表面叠半透明白（elevation 0/1/2/3/4/6/8/12/16/24dp ↔ **0/5/7/8/9/11/12/14/15/16%** 白色覆盖）；M3 改为固定色调的 surface container。⚠️ Material 明确把「用浅色辉光代替深色阴影来表达层级」列为 **Don't**——这条恰好是 HUD 风格最容易犯的错。
4. **品牌色在深色下要降饱和**。原文：满饱和色「don't pass WCAG's… 4.5:1」且会在深底上产生**光学震颤（optical vibration）**导致眼疲劳。做法不是变灰，而是取调色盘浅端；Material 自己把 `#B00020` 叠 40% 白变成 `#CF6679` 才敢用在深色。
5. **对比度是硬指标，不能四舍五入**。三条门槛：
   - **SC 1.4.3（AA）**：正文与文字图像 ≥ **4.5:1**，大字（≥18.66px 粗体 / ≥24px）≥ **3:1**（[contrast-minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)）
   - **SC 1.4.11（AA）**：UI 组件与图形对象 ≥ **3:1**（[non-text-contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)）
   - **SC 1.4.1（A）**：**颜色不能是唯一的信息载体**（[use-of-color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)）

#### 3.2.2 怎么自己验证（不靠感觉）

- **公式**：每通道 `c/255`，`c ≤ 0.04045` 时取 `c/12.92`，否则 `((c+0.055)/1.055)^2.4`；相对亮度 `L = 0.2126R + 0.7152G + 0.0722B`；对比度 `CR = (L亮+0.05)/(L暗+0.05)`。
- **工具**：[WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/)（URL 后加 `&api` 直接出 JSON，可脚本化）、[Chrome DevTools 的对比度检查](https://developer.chrome.com/docs/devtools/accessibility/contrast)、[Apple 辅助功能审计](https://developer.apple.com/documentation/accessibility/performing-accessibility-audits-for-your-app)、Android Accessibility Scanner。
- **Flutter 侧**：没有内置检查器，但 `Color.computeLuminance()` 就是上面的相对亮度，**可以直接写成单元测试断言**：`(a.computeLuminance()+0.05)/(b.computeLuminance()+0.05)`；再用 `MediaQuery.highContrastOf(context)` 响应系统「增强对比度」。

#### 3.2.3 落到这个项目：实算数字与判断

**能放心用的：**

| 组合 | 对比度 | 结论 |
|---|---|---|
| `#38E1FF` on `#03060E` | **12.91:1** | 主强调色非常安全（在 `#0A0E1A` 上 12.27:1） |
| 七色稀有度 on `#03060E` | F 7.97 / E 11.63 / D 9.46 / C 7.45 / B 12.14 / A 8.95 / **S 6.25** | **全部过 AA**；最低的 S 红 6.25 过 AA 但不到 AAA 7:1 |
| 87% 白 `#DEDFE0` 作正文 | 15.19:1 | 几乎正对 Material 的 15.8:1 目标 → **建议正文用它，纯白只留给大字与等宽数值** |

**四个真实风险点（这才是「看起来像深色 UI 但不好用」的来源）：**

1. **用「颜色 + 低不透明度」当次级文字会崩**：S 红 60% → **2.78**、C 紫 60% → 3.25、F 灰 60% → 3.41、D 蓝 60% → 3.89，**全部 < 4.5**。次级文字请用 **60% 白（≈7.3~7.5:1，随 alpha 合成口径略有差异）**，别拿稀有度色降档当灰字用。
2. **稀有度色块上压白字全崩**：E 绿上白字 **1.74**、F 灰 2.54、S 红 3.24。色块上的文字必须用深色 `#03060E`（6.25~12.14，全达标）。
3. **色盲下七色互相分不开**（红绿色盲模拟）：C 紫 vs F 灰 **1.04**、C 紫 vs S 红 1.04、D 蓝 vs A 橙 1.09、D 蓝 vs C 紫 1.18。→ **稀有度必须同时带字母 F/E/D/C/B/A/S**（项目现在确实带了，这是对的），不能只靠颜色（SC 1.4.1）。
4. **辉光会吃掉正文**：青辉光 15% 叠底 → 白字 15.55；25% → 11.74；40% → 7.33；**60% → 仅 4.08，跌破 AA**。→ **辉光只允许在文字下层且强度 ≤25%；正文与长文本区一律不铺辉光/扫描线。**

**关于「层级」的一条实测结论**：深色底上靠明度分层，相邻档之间对比只有 **1.03~1.05**，肉眼几乎分不出来。所以层级**必须**配合 1px 描边（对底 ≥3:1，SC 1.4.11）或位移/尺寸/发光边框。建议五档：`#03060E` 底 → `#0A0E1A` 页面 → 面板 +4% 白 → 悬浮 +8% → 模态 +12%。

#### 3.2.4 三条先记住

1. **深色不是把背景刷黑**：层级 = 表面变亮 + 描边，**不要用辉光代替表面差异**（官方点名的反例）。
2. **4.5 / 3 / 3 三条线**分别来自 **SC 1.4.3 / 1.4.11 / 1.4.1**；任何改色/改透明度后都要重算，且不能四舍五入。
3. **你的主色没问题，问题在四处**：颜色+透明度当次级文字、稀有度色块压白字、辉光铺正文、只靠颜色区分稀有度。

> 补充参考：[NN/g · Dark Mode vs. Light Mode](https://www.nngroup.com/articles/dark-mode/)（深色在小字近距离阅读上其实更差——用来校准「深色=更舒服」的预期）、[web.dev · prefers-color-scheme](https://web.dev/articles/prefers-color-scheme)、[Flutter · 无障碍与 UI 设计](https://docs.flutter.dev/ui/accessibility/ui-design-and-styling)。

#### 3.3.5 避坑清单

1. **只收藏美图当灵感**——收藏越厚判断力不涨。改法：每次只带**一个具体问题**去看（「空状态该怎么表达」）。
2. **直接抄 Dribbble**——静态概念稿，没有信息架构、真实文案、空/错/加载态，抄完跑不起来。
3. **以为设计 = 配色**——配色是最容易改的一层；高级感来自**间距节奏、字阶层级、对齐与留白**。
4. **忽略排版与间距**——数字用正文字体、行距随缘、间距手调 13/17px，是廉价感的主因（你项目已避开这条，要继续守住）。
5. **把动效当装饰**——答不出「它想告诉我什么」的动效就该删。
6. **只学工具不学判断**——先建立判断标准（四原则、十大启发式），再谈 Figma。
7. **术语混乱导致沟通失真**——统一说「层级 / 字阶 / 间距节奏 / 对比度 / 反馈 / 状态」，别说「高级一点」「科技感强一点」。

#### 3.4.3 状态管理：要不要引入 Riverpod？——**暂不引入**

- **官方立场**：[state-mgmt/options](https://docs.flutter.dev/data-and-backend/state-mgmt/options) 明确**不给任何第三方包背书**，只列三种内置方案（`setState` / `ValueNotifier`+`InheritedNotifier` / `InheritedWidget`+`InheritedModel`），第三方统一导向 [pub.dev 话题页](https://pub.dev/packages?q=topic%3Astate-management)。
- **本仓库现状（已核实）**：`lib/state/` 11 个文件全是纯 Dart 数据类，**唯一一个 `ChangeNotifier` 是 `app_clock.dart:15`**；全仓 grep `riverpod|provider|bloc|get_it` **零命中**。也就是说 AGENTS.md 里「状态管理建议 Riverpod」**从未落地**。
- **判断：现在别引入。** ①官方不背书，这是团队选择；②现有 34 个测试文件大量直接构造 `HostState`/`QuestFlow` 做纯逻辑单测，引入 Riverpod 要把测试重写成 `ProviderContainer`，收益（编译期依赖检查）远小于 30+ 文件的迁移风险；③**真正的痛点不在这**——是 `main.dart` 已经 2065 行、一个巨型 `StatefulWidget` 持有全部演出状态。
- **建议的中间态**：先用官方的 `InheritedNotifier`/`ValueNotifier` 把「演出编排状态」从 `main.dart` 摘出来；等真需要跨页共享 + DevTools 状态回溯时再评估 [Riverpod 3.x](https://riverpod.dev)（有中文文档，且能与 `ChangeNotifier` 共存，迁移是渐进的）。

#### 3.4.5 ⚠️ 顺带查出的一个真 bug（已复核）

> **`RingField` 的 `ringMul` 参数是死的 → 「认输时把失败那一环掐暗」从未生效。**

证据链（三处都已亲自读过）：

1. `main.dart:936` 确实传了：`ringMul: fail ? _ringMul : null`；
2. 但 `ring_painter.dart:64-71` 的 `RingField.build` **构造 `RingFieldPainter` 时没有把它传下去**（widget 第 31/51 行声明了、painter 第 85/94 行接收了、第 188 行也确实用它算 `dim`）；
3. `RingFieldPainter.shouldRepaint`（第 305-310 行）**也没有比较 `ringMul`** —— 即便补上透传，参数变化也不会触发重绘。

**影响**：失败/认输场景下环场本该有一环变暗，现在是全部照常亮着——属于「机制已实现但没接线」的静默失效。修法：build 里补 `ringMul: ringMul`，`shouldRepaint` 里补 `!listEquals(old.ringMul, ringMul)`，并写一条 widget test 断言传 `[1, 0.3]` 时 painter 拿到非空 `ringMul`。**本文档不改代码**，留作你的第一张卡（正好是 §4 的练习 1）。

### 4.1 一句话记住这个项目的设计纪律

- **原型即规格**：任何视觉/动效改动，先在 `prototype/` 里改，再搬 Flutter。
- **单一真源**：颜色/字体/数值/时长，只有一个地方能改。
- **动效只用 transform + opacity**（性能铁律），弹簧优先，禁止线性匀速。
- **稀有度色只用于稀有度**，界面 chrome 只用电光青。
- **降级要有兜底**：LLM 挂了走固定文案、Live2D 挂了退回全息剪影、动效关了功能照用。

## 5 · 一页速查：如果你只有两小时

**目标不是「学会设计」，而是「两小时后你能用正确的词判断自己的界面，并知道下一步该学什么」。**

| 时间 | 做什么 | 做完你会得到 |
|---|---|---|
| **0:00–0:20** | 读本文 **§2.2 术语表** + **§2.3 Fluent 三种含义** | 别人说「token / 层级 / 对比度 / 缓动 / 材质」你不会再懵；知道「Fluent」不用全学 |
| **0:20–0:50** | 读 Fluent 2 的 [Design tokens](https://fluent2.microsoft.design/design-tokens) + [Web Alias Color Tokens 全表](https://fluent2.microsoft.design/color-tokens2) | **两层 token**（原始值 → 语义名）的心智，以及一张可直接对照的深色色板表 |
| **0:50–1:25** | 看 Apple《Designing Fluid Interfaces》[中文字幕版](https://developer.apple.com/cn/videos/play/wwdc2018/803/)（约 35 分钟） | 你项目最缺的那一课：**跟手、可打断、有惯性**。看完再看自己的「按住 0.9 秒接单」「拔单」会有一堆新想法 |
| **1:25–1:50** | 读 Material 的 [Dark theme 页](https://m2.material.io/design/color/dark-theme.html)，再对着本文 **§3.2.3** 的四条风险点自查 | 知道自己的深色 UI 哪里「看着高级但不好用」——尤其是次级文字、稀有度色块白字、辉光铺正文这三处 |
| **1:50–2:00** | 打开 [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/)，把你界面上最常用的一组前景/背景色各算一遍 | 一个可复用的硬指标习惯：**改色之后必须重算，不能四舍五入** |

**两小时之后的第一件事**：回 §4，做**练习 1（修 `ringMul` 真 bug）** 和**练习 2（收时长 token）**——一小时内能完成，而且是「学到的概念立刻变成仓库里的真实改进」。

### 5.1 三个「千万别学错」的提醒

1. **别从「配色」开始学**。新手最常把设计等同于配色，结果做出来的东西颜色没问题但**层级、间距、排版全乱**。真正的入门顺序是：**排版 → 间距 → 层级 → 颜色 → 动效**。
2. **别拿别人的静态美图当标准**。灵感网站上的图是**单帧、无交互、无真实文案**的。你的界面要承受长中文、空态、错误态、极端数据——这些东西美图里都没有。
3. **别把动效当装饰**。你这个项目最大的差异化资产恰恰是「手感」（弹簧、过冲、逐帧结算）；动效是用来**说明因果**的（谁从哪来、响应了我的什么操作），不是为了「看起来炫」。
