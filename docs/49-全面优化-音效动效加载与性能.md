### C. 「换目标」模块（重写）

旧实现是**上一代视觉体系**：`AskField`（旧 `C`/`F` 令牌、底部输入条）+ `_GoalChangeChrome`（左上 ← 圆）浮在主线页上，
与 v3 ref 体系（斜切转场、`RefButton`、玻璃卡、eyebrow + h1 抬头）完全不是一套语言；而且提交后只有 1.4s 的一句台词，之后几十秒无任何反馈。

重写为独立场景 `RefGoalSwap`（`lib/ui/ref/ref_goal_swap.dart`）：

- 进出：主线页「换目标」→ `_go('swap')` 斜切转场；× / 返回键 → `_go('main', back: true)`
- 版式：与主线/绑定页同一套 —— eyebrow `REWRITE · 换目标` + h1 + ×；**当前主线卡**（目标原文、进度 N/M、已过天数，红色提示「确认后旧清单撤下」）；
  SYSTEM 台词框（46 核心 + 打字机）；新目标输入 + 预设词 + 「先问小祥」；主键【确认换线】
- 加载：提交后整块换成 `RefPlanLoading`（见 D1）；失败时退回输入态，红字给出原因，可直接重试
- 成功：斜切转回主线页，新清单发牌入场

### E. 性能（iPhone 15 Pro Max 卡顿 + 发热）

| # | 根因 | 修法 | 收益 |
|---|---|---|---|
| E1 | `Info.plist` 开了 `CADisableMinimumFrameDurationOnPhone` → ProMotion 设备跑 **120Hz**。App 里常驻循环动画多（天幕、核心、委托球、按钮扫光、卡面全息…），任何一个 Ticker 在跑都会让引擎**每秒合成 120 帧整屏** | 去掉该键，回到 60Hz 上限 | 常驻动画的 CPU/GPU 开销直接减半；帧预算从 8.3ms 放宽到 16.7ms，掉帧（卡顿）同步减少 |
| E2 | 卡轮播拖动时**每帧 setState 重建所有可见卡面**（`RefTCard` 2700 行的大组件），且压暗值每帧变 → 卡面 RepaintBoundary 每帧失效、连带 70px 大投影每帧重栅格化 | 卡面按（序号, 焦点, 尺寸）缓存，只有焦点切换才重建；压暗改为轮播自己在卡外叠一层圆角暗片 | 拖动时卡面零重建零重绘，只剩合成层变换 |
| E3 | 执行页证据缩略图：重启后的证据走 `FutureBuilder(future: visionReadBytes(...))`，**future 在 build 里新建** → 执行页时钟 250ms 一次重建 → 每秒 4 次读盘 + 4 次原图解码 | 读盘 Future 按路径缓存 | 消除持续 IO 与解码 |
| E4 | 证据图按**原图分辨率**解码（1200 万像素 ≈ 48MB 位图）塞进 82px 槽 | `Image.memory(..., cacheWidth: 360)` 降采样解码 | 单张内存从几十 MB 降到 < 1MB |
| E5 | 每次触屏（节流 1s）都 `setState(_lastAct)` → **整个 AppShell 重建**；认输按住时**每帧** `setState(_quitP)` → 整棵树每帧重建 | `_lastAct` 不进 setState（只有每秒的 `_onSecond` 读它）；`_quitP` 改 `ValueNotifier`，只重建暗幕 | 交互期间主壳重建次数大幅下降 |
| E6 | LLM 设置是不透明整页，打开时底下的大厅/天幕动画照跑 | — | 整页打开时用 `TickerMode(enabled: false)` 冻结下层所有 Ticker |
| E7 | `RefReveal` 入场模糊在省电档也跑（每次换页 5~7 层同时做 ImageFilter.blur） | — | 省电档（`Fidelity.lowPower`）跳过模糊，只保留位移 + 透明 |

### F. 换目标拆解太慢（宿主真机：2 分钟还没拆完）

| # | 根因 | 修法 |
|---|---|---|
| F1 | 匹配、拆解两步都挂了 `get_status` / `recall`，而且提示词与 `set_plan` 描述都**明确要求**「先 get_status、必要时 recall，再交」。可宿主档案（statusLine）与相关记忆（`MemoryStore.digest`）本来就写在系统提示里 —— 每步都白白多一整轮往返。推理模型一轮 10~40s，换目标最少串行 4 轮 | 两步都只挂交卷工具（`set_goal_category` / `set_plan`），提示词改为「档案与记忆已在上面，直接据此拆、一次交上来」。常规情况 4 轮 → 2 轮，耗时约减半 |
| F2 | 换目标 / 绑定的 catch 只接 `PlanFailure`：链路里冒出别的异常时加载卡**永远不撤**，看起来就是「一直在拆」 | 改为接住一切异常，统一落成可见的失败（`badResponse · 意外异常：…`），旧主线不动、可直接重试 |

| F3 | **真正的大头**：条数 = 期限天数（`planTaskCountFor`），「三个月跑完半马」= **90 张**、「半年减重」= 180 张，一次 `set_plan` 要吐几千~上万 token 的 JSON → 单轮 90s 超时，或被 `max_tokens` 截断成残缺数组 → 报错重试，越重试越慢（宿主真机：2 分钟后报错） | 长清单**分段并行拆**：每段 ≤ 12 张（`kPlanSegmentSize`），最多 6 段同时请求（`kPlanSegmentConcurrency`）。档位阶梯在切段时预分配（每段一个区间，相邻段首尾相接，末段收 S 级兑现单），每段用自己的 `set_plan` 按段校验，拼回后仍过全量 `validatePlan`。仍然全部走 LLM、没有模板。90 张 ≈ 8 段一波并行，耗时≈单段（15~30s）+ 匹配；加载卡第 2 步显示「n/8 段并行」 |

> 仍需知道：段数超过 6 时分两波；单段超时上限 90s；任何一段失败整份作废（不拼半份计划），旧主线不动。

## 二、交付后需宿主确认的点

1. 主线页左右滑卡：每跨一张一声轻「咔」；滑到两头再拽一声闷「嗒」
2. 系统设置抽屉：从底部滑上来、点空白处滑下去
3. LLM 设置：斜切转场进入，标题/各分区逐层显影；关闭同样斜切退出
4. 重置存档 → 绑定：确立目标后立刻出现「SYSTEM 正在拆解」加载卡（三步进度 + 计时），不会再像卡死
5. 主线页【换目标】：斜切进入新页面；提交后同一套加载卡；成功后斜切回主线页、新清单发牌
6. 整体：长时间停在大厅/主线页，机身温度应明显低于改动前（帧率上限 60Hz）
